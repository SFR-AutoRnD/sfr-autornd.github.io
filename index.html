Why We Built AutoR&D

Performance engineering is some of the most valuable — and scarcest — work in software. The wins hide in mature codebases that millions of applications depend on, and every optimization carries a claim — "this version is faster, and it computes exactly the same thing" — that has to be tested. A profiler tells you where time goes; it doesn't tell you what to do about it, whether a fix works, or whether it quietly broke a floating-point edge case.


We built an agent that behaves like a careful research scientist: skeptical of its own ideas, obsessed with controls, and unwilling to ship anything it can't prove. We call its outputs artifacts — a working patch bundled with the benchmark evidence and analysis that justify it. This page shares the first four codebases it improved: three in the open-source ecosystem, one in Salesforce's own AI infrastructure.

How AutoR&D Works

🧪

Built, Run, and Measured

Every candidate is built, run, and measured against the unmodified baseline — same hardware, same inputs, paired runs in alternating order across multiple seeds, so noise cancels out.

✓

Correctness Is a Gate

Patched and unpatched systems are fed identical inputs and compared exactly — hashes, dtypes, edge cases down to the sign of a floating-point zero. Any observable change means automatic rejection.

📊

Statistics Before Headlines

Every reported number carries confidence bounds from repeated measurements. A flashy median with a shaky interval doesn't get promoted, no matter how good it looks.

🚫

It Rejects Its Own Ideas

One clever kernel rewrite showed a small win in one phase and a regression in another — AutoR&D flagged the mixed evidence and held it back itself. Negative results are recorded too.

We didn't hand AutoR&D toy problems — we aimed it at three heavily used, heavily optimized open-source libraries — pandas, USearch, and hnswlib — plus one of our own production systems. It found something real in all four.

Open Source · Dataframes

pandas: three speedups in the workhorse of data science

Up to 1.84× on nullable dtypes 4–28% faster primary workloads Up to +64.6% best case 136K checks, 0 mismatches

pandas must handle every data type, missing-value convention, and memory layout — and that generality has a cost: hot operations sometimes do conversion, masking, and copying work even when the data is already in ideal form. AutoR&D's answer: check first, then take the express lane. A narrowly guarded fast path serves data whose layout qualifies; everything else falls through to pandas' unchanged general implementation.

Optimization 1Row-wise math on nullable dtypes

pandas' nullable integer, float, and boolean columns — including their Arrow-backed variants — take their own route for row-wise sum, prod, min, and max: the frame is flattened and run through the groupby kernels, which meant first building a "row label" for every single element — a throwaway array as large as the frame itself — just to tell the kernel which row each value belongs to. AutoR&D's patch views the existing data and mask buffers in the layout the kernel already expects and reduces with a single group, so that label array is never allocated and the kernels and reduction order stay exactly as they were. Across pandas' own 40-cell benchmark that's 1.22–1.84× faster (median 1.38×) with every confidence interval above parity, and 12–15% lower peak memory on a 10-million-element frame.

Technical details: formulation & implementation
Formulation

For a frame X with n rows and c columns that share one nullable dtype, pandas evaluates X.sum(axis=1) by concatenating the columns into a single 1-D extension array A of length n·c, laid out column-major (A[c·n + r] = X[r, c]), and calling the groupby aggregation kernel with a label vector L = tile(arange(n), c) so that group r collects row r. That label vector is an n·c array of 8-byte integers that exists only to tell the kernel which row each element belongs to.

The new route views the same data and mask buffers as a (c, n) matrix, transposes to (n, c), and calls the kernel with one group and c ids. Each of the kernel's n "columns" is now one frame row, aggregated over its c observations. Every output cell consumes the same values in the same column order as the labelled formulation, so results are bit-identical; the only thing that disappears is the label array.

Implementation
  • BaseMaskedArray._groupby_op_axis1(how, nrows, ncols, min_count, skipna) reshapes _data/_mask as views and calls WrappedCythonOp._cython_op_ndim_compat(values, ngroups=1, comp_ids=zeros(ncols), mask, result_mask); it raises NotImplementedError for anything it doesn't handle so the caller falls back.
  • ArrowExtensionArray._groupby_op_axis1 covers the eleven Arrow int/uint/float/bool types by delegating through _to_masked() and converting the result back; string, decimal and timestamp Arrow types fall through.
  • DataFrame._reduce tries the route first for sum/prod/min/max and otherwise continues to the existing np.tile label path. New ASV benchmarks (FrameOpsAxis1EA, FrameOpsAxis1EAPeakmem) cover it.
# pandas/core/arrays/masked.py
def _groupby_op_axis1(self, *, how, nrows, ncols, min_count, skipna, **kwargs):
    if how not in ("sum", "prod", "min", "max") or self.size != nrows * ncols:
        raise NotImplementedError                     # caller falls back to _groupby_op
    op = WrappedCythonOp(how=how, kind=WrappedCythonOp.get_kind_from_how(how),
                         has_dropped_na=False)
    values = self._data.reshape(ncols, nrows).T       # views of the existing buffers
    mask   = self._mask.reshape(ncols, nrows).T
    result = op._cython_op_ndim_compat(values, min_count=min_count, ngroups=1,
                                       comp_ids=np.zeros(ncols, dtype=np.intp),
                                       mask=mask, result_mask=result_mask, skipna=skipna)
    return self._maybe_mask_result(result.squeeze(axis=1), result_mask.squeeze(axis=1))
Evidence
  • 134,064 differential cases (141,120 calls) across every supported dtype, skipna, min_count 0–4, degenerate shapes, infinities and NA patterns: zero result, mask, dtype, index-dtype or exception differences. 1,584 of 1,584 routing checks used the new kernel; a monkeypatched _groupby_op proves the old path is never reached.
  • ASV: 29 of 40 timing cells flagged improved (ratios 0.51–0.82), 10 more faster with overlapping intervals, one neutral, none slower. Paired CPU-pinned study: 1.215–1.837× (median 1.377×), every bootstrap interval above 1.
  • Peak memory on a 2,000,000 × 5 frame: 449 → 396 MB (sum, Int64), 472 → 401 MB (sum, float64[pyarrow]); 437 new tests and 44,458 existing tests pass.

Optimization 2Counting and de-duplicating strings

For nullable string columns, duplicated() and value_counts() now hand their backing array straight to pandas' own hashing kernel — 4.4–12.2% faster on million-value workloads, with peak memory for value_counts down by about a third. Total change: a 28-line diff.

Technical details: formulation & implementation
Formulation

Write the baseline operator as F0 and the candidate as F1. A route is a guard g, a kernel K and a reconstruction Q: F1(x) = Q(K(P(x))) when g(x) = 1, and F0(x) otherwise, where P is a zero-copy projection of the physical representation. The obligation is equality of the full public projection — values or exception type, value dtype, shape, index dtype, index values and names — for every input, so the guard has to cover aliasing and mutability as well as dtype.

Here the representation is a StringArray whose backing store is an object ndarray with pd.NA as the sentinel. The inherited duplicated first materializes an NA mask and the generic value_counts exports via to_numpy, hashes, then converts the result index back to the extension dtype — adapter work around a kernel that already accepts the backing array as-is.

Implementation

One file, pandas/core/arrays/string_.py, 28 lines inserted and 2 deleted. The guard for duplicated is that the sentinel is exactly pd.NA; value_counts additionally requires dropna=True. No new hash table, encoding or NA rule is introduced — the behavioral risk sits entirely in the guard and the reconstruction.

# pandas/core/arrays/string_.py
def duplicated(self, keep="first"):
    if self.dtype.na_value is libmissing.NA:
        return duplicated(self._ndarray, keep=keep)          # algorithms-layer kernel, no NA mask pass
    return super().duplicated(keep=keep)

def value_counts(self, dropna=True):
    if self.dtype.na_value is libmissing.NA and dropna:
        result = value_counts_internal(self._ndarray, sort=False, dropna=True)
        index_arr = self._from_backing_data(np.asarray(result.index._data))
        result = Series(result._values, index=Index(index_arr, copy=False), copy=False)
    else:
        result = super().value_counts(dropna=dropna)

  • 130-case differential matrix over object, Python-string and Arrow-string representations; ASCII, empty, embedded-NUL, composed/decomposed Unicode, CJK and emoji payloads; every NA variant; all keep modes and value_counts options. Baseline and candidate serializations share the same SHA-256.
  • 30 paired timings per case in alternating order on a pinned core: all four activated routes have simultaneous 95% upper ratio bounds below parity (0.899–0.970); the intentional Unicode fallback control does not (1.025), confirming the route counter.
  • Fresh-process memory: value_counts peak RSS increase 37.13 → 24.45 MB, traced peak 31.65 → 24.66 MB; duplicate detection non-increasing on both metrics.

Optimization 3Row-wise math on numeric frames

sum, prod, min, and max across rows used to allocate fresh intermediate arrays for every internal block; the patch folds blocks into one reused accumulator. That's 12–28% faster on a typical 100,000-row mixed frame — and up to 64.6% on the fragmented frames real pipelines accumulate.

Technical details: formulation & implementation
Formulation

For sum/prod/min/max with axis=1 the baseline avoids a transpose: each physical block is reduced to a length-n vector middle, the first is copied into result, and every later block produces a fresh ufunc(result, middle). With B blocks that is B block temporaries, one copy and B − 1 combine temporaries; nullable float sum/prod add mask and filled-copy allocations inside nanops. The candidate reduces the first eligible block straight into an owned accumulator and folds each later block through one reused scratch array, combining in place — one accumulator and at most one scratch regardless of B.

Bitwise fidelity is the constraint. Float sum/prod are identity-seeded in the baseline, and that seed is observable: (+0.0) + (−0.0) is +0.0, whereas copying the first row would preserve −0.0. The fold therefore seeds with 0 or 1, visits rows in order, and substitutes the identity for NaN only on rows that contain one. Integer ops and min/max use ufunc.reduce(..., out=).

Implementation

pandas/core/frame.py, 151 lines added, mostly guards. A block is eligible when it is a C-contiguous, native-byte-order 2-D ndarray of int64/uint64/float32/float64 whose ufunc.resolve_dtypes is a no-cast operation; the accumulator must be owned, writable, shape-compatible and non-aliasing. Unlike dtypes are accepted only when one side dominates promotion (the accumulator is promoted once); mixed promotions such as int64 + uint64 → float64 stay generic. min/max use the route from 4,096 rows; sum/prod at any length.

Salesforce Internal · LLM Training

SFR-RL: taming memory and speed in our own RL stack

−39% peak training memory Up to 3.14× generation throughput Token-for-token identical outputs

The most satisfying test was pointing AutoR&D at our own infrastructure: SFR-RL, the reinforcement-learning stack Salesforce AI Research uses to post-train large models. (SFR-RL is internal, so this page covers the results and keeps the recipes in-house.)

Optimization 1Memory: from roulette to guarantees

In RL training the model generates its own training data, so each step's memory footprint is drawn fresh every update — and one unlucky draw can blow past GPU memory late in an expensive run. AutoR&D's improvements make peak memory predictable and bounded by configuration: on a demanding long-context workload, peak memory fell from 128.5 GiB — an out-of-memory crash — to a stable 78.6 GiB across 19 consecutive updates, with the training computation itself unchanged.

Technical details: formulation & implementation
Formulation

In supervised training the memory-relevant shape of an update is a configuration choice, so one representative step can be profiled and the settings stay valid. RL post-training removes that property: each update consumes trajectories the current policy just generated, so the token count, the sequence-length mixture and — because routing is a learned function of content — the expert-routing matrix of a mixture-of-experts model are all sampled, and are only known after generation has committed them. Two things follow. What a configuration has to survive is the range the sampler admits, which is far larger than anything a run happens to exhibit: on the studied one-node run the token packer admits a worst-case dispatch demand more than three times the worst of 7,440 logged routing matrices. And the peak lands inside a checkpointed backward pass, after rollout, scoring and a full forward have been paid for, so an overflow discards the whole update.

The design requirements AutoR&D worked to were therefore: (1) a memory bound that is a function of configured constants, never of the observed workload; (2) a bound that holds during checkpoint recomputation as well as in the forward pass; (3) fail-closed behavior — stop deterministically before any collective is issued when a draw cannot be honored; (4) exact computation — no change to tokens, routing, expert assignment, precision, gradients or optimizer semantics, because anything that perturbed the policy would also perturb every later update.

What changed

Two complementary mechanisms, each targeting one of the two dominant activation live sets in the checkpointed backward (transient expert-dispatch buffers and long-lived decoder checkpoint boundaries), give those live sets bounds that follow from the configuration alone and rebuild anything route-scale on demand during recomputation. They compose with activation checkpointing, ZeRO-3 partitioning and CPU optimizer offload, which the baseline already used. The mechanism internals are SFR-RL's and are not described here.

Evidence
  • Same configuration, same workload: the baseline exhausts device memory during its first checkpointed backward at a 128.5 GiB peak allocation; with the mechanisms enabled the run sustains 19 consecutive updates at a 78.6 GiB peak with at least 28 GiB of physical headroom.
  • The bounded live sets match their configuration-derived ceilings to three decimal places at the largest observed step, confirming the bounds come from the configuration and would hold for any draw.
  • Because trajectories are not replayed identically between configurations, the before/after contrast is reported as a single system-level observation without a matched per-mechanism decomposition.

Optimization 2Throughput: the same answers, three times faster

On the serving side of the loop, AutoR&D cut median time per generated token by 60–69% across four workload types — up to 3.14× baseline throughput on long-output workloads — with the accelerated path verified to produce exactly the same tokens, request by request, in every confirmation run.

Technical details: formulation & implementation
Formulation

Two endpoints are kept separate on purpose. For a request with n output tokens, time-to-first-token TTFT = tfirst − tsubmit and time-per-output-token TPOT = (tlast − tfirst) / (n − 1); goodput is committed output tokens per second of wall-clock time. In autoregressive serving TPOT is dominated by the number of full target-model passes per committed token, while TTFT is governed by queueing, prefill and dispatch. The change reduces target passes per committed token on the serving path while keeping the target model the sole authority for every visible token, so the externally visible sequence is exactly the target's greedy sequence, and removes a device-to-host synchronization and a per-forward metadata translation from the remaining hot path.

Acceptance rule

The unit of replication is a fresh server-process restart: ten balanced-order control/treatment restart pairs per workload, two-stage bootstrap intervals (restart blocks, then requests within a block), and exact one-sided sign tests. A pair is admissible only if prompts, lengths, arrivals, sampling, parallelism, attention and graph policy all match, every request completes, and complete output token IDs match prompt by prompt. Decode acceptance requires both p50 and p95 TPOT ratios and their simultaneous upper bounds to be at most 0.80 with consistent restart direction.

Evidence
  • TPOT p50 down 65.8% (1K/128), 69.4% (8K/2048), 60.8% (32K/512) and 62.3% (paced mix); p95 down 47.5–68.8%; ten of ten restart signs favorable in every cell (p = 2−10). Decode goodput 2.30×, 3.14×, 1.80× and 1.07× control respectively — the paced mix is arrival-limited.
  • Output equality: 320 matched requests per fixed-workload arm and every paced restart produced identical token sequences prompt by prompt.
  • First-token latency is a separate objective: neutral-to-better on the fixed workloads, but the paced mix regresses p95 TTFT by 18%, driven by its long-prompt/short-output stratum. The path is therefore deployed for decode-heavy traffic and ordinary decoding is kept for first-token-tail-sensitive traffic.

💡 Why it matters

Faster iterations and no more lost runs — our researchers feel this one every day. And because outputs are verified identical, the speedups are free: no accuracy trade-off, no behavioral drift.

USearch: skipping the math that vector search repeats millions of times

+17.5% search throughput (GCC 11) +7.4% (GCC 13) +4 bytes per vector Same neighbors · recall within 0.01 pt

USearch is a compact, high-performance vector-search engine that ships as a single header and is embedded in databases and AI applications. Its cosine-similarity kernel — the default for comparing text and image embeddings — needs the length of both vectors for every comparison. AutoR&D spotted a redundancy: the length of a stored vector never changes, yet the built-in kernel recomputed it on every one of the hundreds of comparisons a single query performs — millions of times across a workload.

The patch caches each stored vector's length once, in a 4-byte lock-free "sidecar" that follows the vector through inserts, removals, compaction, copies, and reloads. The query's length is computed once per search, so each comparison shrinks to a dot product and one division: three multiply-adds per element become one, and two square roots become none. The route is deliberately narrow — custom metrics, memory-mapped indexes, non-finite values, and builds that use an external SIMD library all keep the original path — and the on-disk index format is unchanged.

On a one-million-vector Wikipedia-embedding index, single-core search throughput rose 17.5% with GCC 11 and 7.4% with GCC 13, positive in every paired round, while the graph traversal stayed identical: the same 926.5 distance evaluations and 75.8 visited nodes per query. The cost is 4 bytes per vector (+0.3% memory). Across 10,240 top-10 results, distances agreed to within 4×10−7 and recall was unchanged with GCC 11 and within 0.01 point with GCC 13; the change passed the C and C++ suites under Address-, UndefinedBehavior- and ThreadSanitizer, from C++11 through C++20.

Technical details: formulation & implementation
Formulation

Cosine distance is d(a, b) = 1 − a·b / (‖a‖ ‖b‖). USearch's built-in f32/bf16 kernel evaluates a·b, ‖a‖² and ‖b‖² in one pass — three multiply-adds per element — followed by two square roots and a division, for every one of the ~927 comparisons an HNSW query performs. In that setting b is a stored member vector whose norm is fixed from insertion, and a is the query, whose norm is the same for every comparison in the search. Caching ‖b‖ per slot and computing ‖a‖ once per query leaves one multiply-add per element, one multiply and one division: the expression 1 − a·b / (‖a‖ ‖b‖) is algebraically identical to the kernel's 1 − a·b / (√a² √b²), differing only in floating-point rounding.

Implementation
  • Sidecar. index_dense_gt gains cosine_norms_: one lock-free std::atomic<uint32_t> per capacity slot holding the raw bits of the f32 norm, or a quiet-NaN sentinel (0x7fc00000). Insertion publishes with a release store after the vector bytes are written; search loads with acquire before reading them; reserve, clear, compact, copy, load and metric changes use relaxed accesses because they exclude concurrent insertion. A C++11-compatible static_assert guards lock-freedom.
  • Search proxy. metric_proxy_cosine_norms_t carries the prepared query norm and calls cosine_distance_with_valid_norms; a slot holding the sentinel falls back to the full kernel per comparison, and a non-finite query bypasses the route for the whole search.
  • Eligibility and provenance. supports_cosine_norm_cache() identifies the built-in kernel by the address of the exact metric_cos_gt instantiation plus its dimension argument — deliberately not the routing trampoline, which identical-code-folding linkers (/OPT:ICF, --icf=all) can merge, so a cosine-labelled user callback can never be captured. Custom metrics, NumKong-supplied kernels, memory-mapped views, external-vector indexes and other scalar kinds keep the original path.
  • Lifecycle. reserve grows the sidecar with capacity; add/update populate a slot; remove and clear invalidate it; compact remaps and repopulates; copy duplicates a valid sidecar; load rebuilds it; views bypass it; a metric change builds and populates replacement state before committing, so an allocation failure leaves the index untouched. The sidecar is never serialized, so the file format is unchanged.
  • Fast-math safety. All finiteness classification is done on integer bit patterns, and the accumulated norm is laundered through a volatile before inspection so -ffast-math builds cannot assume it finite.
// include/usearch/index_dense.hpp — the search-only proxy's hot path
distance_t f(byte_t const* query, member_at member) const noexcept {
    std::uint32_t bits = index_->cosine_norms_[get_slot(member)].load(std::memory_order_acquire);
    if (!metric_t::is_valid_cosine_norm_bits(bits))            // sentinel: full kernel for this member
        return index_->metric_(query, v(member));
    f32_t member_norm; std::memcpy(&member_norm, &bits, sizeof member_norm);
    return index_->metric_.cosine_distance_with_valid_norms(query, v(member), query_norm_, member_norm);
}
// include/usearch/index_plugins.hpp — one dot product, no square roots
result_t cosine_distance_with_valid_norms(byte_t const* a, byte_t const* b, f32_t a_norm, f32_t b_norm) {
    f32_t ab = cosine_dot_(a, b, dimensions_);
    if (a_is_zero) return b_is_zero ? 0 : 1;                      // zero handling matches metric_cos_gt
    if (b_is_zero) return 1;
    return 1 - ab / (a_norm * b_norm);
}

  • Wiki-1M (1M × 256 f32), identical prebuilt graph in both binaries, one pinned core, 1,024 held-out queries, 16 timed repeats, seven paired rounds: +17.54% median QPS with GCC 11.4 (95% bootstrap +17.14% to +17.76%) and +7.41% with GCC 13.4 (+7.20% to +7.61%); 7/7 rounds positive on both. Computed distances (926.5/query) and visited members (75.8/query) unchanged in every timed row.
  • Memory 1,333,418,176 → 1,337,418,176 bytes at one million slots — exactly four bytes per slot. Load 0.92–0.94 s → 1.04–1.05 s (sidecar rebuilt); 96-thread construction 10.2–10.5 s either way.
  • Result parity over 10,240 top-10 outputs: GCC 11 reordered four positions across two queries with identical neighbor sets; GCC 13 changed twelve positions and one top-10 boundary member; maximum distance change 4.1 × 10−7; recall 0.98574 → 0.98564 at worst. hnswlib: a clean +4% in the engine behind AI retrieval

+4.1% median query throughput Bit-for-bit identical results

hnswlib powers vector search inside databases, RAG pipelines, and recommendation systems, and has been tuned by experts for years — exactly why we chose it. AutoR&D found a remaining win in the batch query path: every query was paying a synchronization cost to borrow scratch memory from a shared pool. Its patch has each worker thread lease that scratch once and reuse it across the batch — roughly 4,000 lock operations collapsed to 32 in the diagnostic workload — while leaving the search logic untouched.

The result: +4.1% median queries-per-second across three independently built indexes, faster in every paired run, with labels, distances, and recall verified identical to the byte.

Technical details: formulation & implementation
Formulation

HNSW traversal needs a scratch "visited" set. hnswlib stores it as a dense generation-tag array: node v counts as visited in the current search when mass[v] == curV, so advancing curV clears the set in constant time and only a generation wrap performs a physical clear. The Python batch path calls searchKnn once per row, and each call locks VisitedListPool to acquire and reset a list and locks it again to return it — about 2Q mutex operations for Q rows, even though a ParallelFor worker executes many rows back to back. Moving ownership from the row to the worker makes that 2W for W active workers: with Q = 2,000 and W = 16, 4,000 lock episodes become 32 (−99.2%). Every row still gets exactly one generation advance; only pool ownership is amortized.

Implementation
  • A non-copyable RAII VisitedListLease: acquisition prepares the first generation, next() prepares each later row, and the destructor returns the list even when a filter callback or query raises.
  • A private search helper, searchKnnWithVisitedList, accepts caller-owned scratch; the public searchKnn wrapper is unchanged, so direct C++ callers and single-row queries behave exactly as before.
  • The batch knn_query keeps one lazily created lease per worker slot. The distance arithmetic, graph layout and serialization are untouched, which is why labels and distances are byte-identical.
// python_bindings — batch knn_query, inside the ParallelFor body
auto& lease = visited_list_leases[threadId];
VisitedList* vl;
if (!lease) {
    lease = index->visited_list_pool_->getFreeVisitedListLease();   // lock once per worker
    vl = lease->get();                                              // first row reset on acquire
} else {
    vl = lease->next();                                             // one generation advance per later row
}
auto result = index->searchKnnWithVisitedList(query, k, vl, filter);
// RAII: the lease returns vl to the pool exactly once, when this worker's batch scope ends
Evidence
  • Invariants checked explicitly: fresh visited set per row (wrap/clearing test), single owner per slot (concurrent-batch test), return on exception (injected exception, then reuse), search equivalence (labels and distances matched), and coverage of L2, inner product, cosine, filters and deletions. An early resize-related segfault was caught in development, fixed, and kept as a regression test.
  • Exploratory A/B on three independently built indexes, order alternated B/C, C/B, B/C, all 31 timed repetitions retained: +4.34%, +4.12%, +3.96% QPS; recall@10 identical to four decimals; peak RSS within ±0.11%; output hashes identical.
  • Reported as an exploratory signal that supports a focused upstream PR; a full preregistered 48-point, five-seed campaign was not run.
