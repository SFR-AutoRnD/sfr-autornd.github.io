Meet AutoResearch: an AI agent that does performance research on real code — and proves it

Most coding agents write code. AutoResearch does something harder: it studies a mature, battle-tested codebase, invents its own optimization ideas, runs controlled experiments, and keeps only the wins it can back with evidence. Its first discoveries are already headed upstream.

The idea

From agents that write code to agents that do research

Performance engineering is some of the most valuable — and scarcest — work in software. The wins hide in mature, heavily-optimized codebases that millions of applications depend on, and finding them takes a rare combination of systems intuition, patience, and experimental discipline. A profiler tells you where time goes; it doesn't tell you what to do about it, whether your fix actually works, or whether it quietly broke something subtle.

That last part is the crux. An optimization is not a code change — it's a claim: "this version is faster, and it computes exactly the same thing." Claims need experiments. So instead of building another code-writing assistant, we built an agent that behaves like a careful research scientist: skeptical of its own ideas, obsessed with controls, and unwilling to ship anything it can't prove.

We call the outputs artifacts: not just a patch, but a patch bundled with the benchmark evidence and analysis that justify it. Below, we share the first three.

Under the hood

How AutoResearch works — a high-level tour

AutoResearch runs a closed loop that mirrors how a human performance researcher operates, with one big difference: it can explore many more ideas in parallel, around the clock, and it never gets attached to a favorite hypothesis.

A few things make this loop work where naive "ask an LLM to optimize my code" doesn't:

It experiments instead of guessing. Every candidate change is built, run, and measured against the unmodified baseline in a controlled environment — same hardware, same inputs, paired runs in alternating order to cancel out noise.

Correctness is a gate, not an afterthought. A candidate that is fast but changes any observable behavior — down to floating-point edge cases like the sign of a zero — is rejected automatically.

It's honest about uncertainty. Results come with confidence bounds, and a candidate whose evidence is mixed gets held back, not hyped. Several of AutoResearch's own inventions didn't make the cut — and that's the system working as intended.

The methodology behind AutoResearch — how it generates hypotheses, allocates its experiment budget, and gates evidence — is proprietary technology that Salesforce has filed patents on, so we're keeping this description intentionally high-level.
The discoveries

Three artifacts, from open source to our own stack

To pressure-test AutoResearch we didn't hand it toy problems. We aimed it at two of the most heavily used — and heavily optimized — libraries in the Python data and AI ecosystem, plus one of our own production systems. It found something real in all three.

1
Open source · vector search

hnswlib: a clean +4% in the engine behind AI retrieval

+4.1% median query throughput Bit-for-bit identical results

hnswlib is one of the world's most widely used approximate-nearest-neighbor engines — it powers vector search inside databases, RAG pipelines, and recommendation systems. It has been profiled and tuned by experts for years, which is exactly why we chose it: any remaining win has to be a genuinely good idea.

AutoResearch found one in the library's batch query path. Each search needs a small piece of scratch memory (a "visited" list) that queries borrow from a shared pool — and in a batch, every single query was paying the synchronization cost of checking that scratch out and back in. AutoResearch's patch has each worker thread lease its scratch once and reuse it across the whole batch: in its diagnostic workload, roughly 4,000 lock operations collapsed to 32 — a 99.2% reduction — while preserving the search logic untouched.

The result: +4.1% median queries-per-second across three independently built indexes, faster in every paired run — with labels, distances, and recall verified identical to the byte.

2
Open source · dataframes

pandas: routing hot paths around work they don't need

4–28% faster on primary workloads Up to +64.6% in the best case 1,910 correctness checks, 0 mismatches

pandas is the workhorse of data science, and its flexibility is the point: the same operation must handle every data type, missing-value convention, and memory layout users can throw at it. AutoResearch noticed that this generality has a cost — hot operations sometimes do conversion, masking, and copying work even when the data is already in the ideal form.

Its answer is a pattern we'd describe as "check first, then take the express lane." A narrowly guarded fast path handles data whose layout already qualifies; everything else falls through to pandas' unchanged, general implementation. AutoResearch applied the pattern in two places:

Counting and de-duplicating strings. For nullable string columns, duplicated() and value_counts() now hand their backing array straight to pandas' own hashing kernel, skipping redundant adapter layers. On one-million-value workloads that's 4.4–12.2% faster — and peak memory for value_counts dropped by about a third. Total size of the change: a 28-line diff.

Row-wise math. Computing sum, prod, min, or max across each row used to allocate fresh intermediate arrays for every internal block of the dataframe. The patch folds blocks into a single reused accumulator instead. On a typical 100,000-row mixed-type frame that's 12–28% faster; on fragmented frames — the kind real pipelines accumulate after many inserts and joins — it reaches 64.6%.

What makes us comfortable proposing this upstream isn't the speed — it's the verification. AutoResearch ran 1,910 differential test cases comparing patched and unpatched pandas on identical inputs: Unicode and emoji strings, missing values, integer overflow, NaN propagation, even the sign bit of floating-point zero. Every output matched exactly. And because the fast paths are guarded, anything unusual simply takes the original code path.

3
Salesforce internal · LLM training

SFR‑RL: taming memory and speed in our own RL stack

−39% peak training memory Up to 3.1× generation throughput Outputs verified token-for-token identical

The most satisfying test was pointing AutoResearch at our own infrastructure: SFR‑RL, the reinforcement-learning stack Salesforce AI Research uses to post-train large models — including the mixture-of-experts models behind our agentic AI work. (SFR‑RL is internal, so we'll share the results here rather than the recipes.)

Memory: from roulette to guarantees. RL training has a nasty property: the model generates its own training data as it learns, so the size and shape of each training step is drawn fresh every update — and a rare unlucky draw can blow past GPU memory at the worst possible moment, destroying an expensive run. AutoResearch produced improvements that make the trainer's peak memory predictable and bounded by configuration rather than by luck: on a demanding long-context workload, peak memory fell from 128.5 GiB — an out-of-memory crash — to a stable 78.6 GiB, and the run sustained 19 consecutive updates with room to spare. Crucially, the training computation itself is unchanged: same tokens, same gradients, same model.

Throughput: the same answers, three times faster. On the serving side of the loop — where the model generates the text that RL learns from — AutoResearch delivered optimizations that cut the median time per generated token by 60–69% across four workload types, lifting generation throughput to as much as 3.14× baseline on long-output workloads. And in keeping with the house rule, the accelerated path was verified to produce exactly the same tokens as the original, request by request, across every confirmation run.

Faster iterations and no more lost runs: our researchers feel this one every day.

Why you can trust it

An AI that shows its work

Anyone can claim a speedup. The reason we're comfortable putting AutoResearch's name on pull requests is the standard of evidence it holds itself to — the same one we'd demand of a human researcher, applied automatically to every candidate.

✓Paired, controlled benchmarks

Baseline and candidate run on the same hardware, same inputs, in alternating order across multiple seeds and process restarts — so noise cancels out instead of masquerading as a result.

✓Exact differential testing

Patched and unpatched systems are fed identical inputs and their outputs compared exactly — hashes, dtypes, edge cases and all. For serving, generated text must match token-for-token.

✓Statistics before headlines

Every reported number carries confidence bounds from repeated measurements. A flashy median with a shaky interval doesn't get promoted, no matter how good it looks.

✓It rejects its own ideas

One candidate — a clever low-level compute kernel rewrite — showed a small win in one phase and a small regression in another. AutoResearch flagged the mixed evidence and held it back itself. Negative results are kept, not buried.

Looking ahead

What's next

These three artifacts are a beginning, not a victory lap. The same loop that found a lock bottleneck in hnswlib and an allocation pattern in pandas generalizes to any system where performance claims can be tested — and most can. We're scaling AutoResearch along three axes:

More targets. Broadening from data infrastructure to the wider open-source ecosystem our customers' AI stacks depend on — and more of Salesforce's own platform.

Deeper autonomy. Letting the agent pursue longer research arcs: multi-step optimization campaigns where one discovery informs the next hypothesis.

Open contribution. Continuing to package discoveries in open-source projects as upstream pull requests, with the full evidence attached — because a speedup only matters once it's in your hands.

We think the future of agentic AI isn't just agents that do what we ask — it's agents that find improvements we didn't know to ask for, and prove they're real. AutoResearch is our first step there.
