Why an AI Researcher, Not a Code Assistant

Performance engineering is some of the most valuable — and scarcest — work in software. The wins hide in mature codebases that millions of applications depend on, and an optimization is not just a code change: it's a claim — "this version is faster, and it computes exactly the same thing." Claims need experiments. A profiler tells you where time goes; it doesn't tell you what to do about it, whether a fix works, or whether it quietly broke a floating-point edge case.


So instead of another code-writing assistant, we built an agent that behaves like a careful research scientist: skeptical of its own ideas, obsessed with controls, and unwilling to ship anything it can't prove. We call its outputs artifacts — a working patch bundled with the benchmark evidence and analysis that justify it. This page shares the first three: two in the open-source ecosystem, one in Salesforce's own AI infrastructure.

How AutoR&D Works

🧪

Experiments, Not Guesses

Every candidate is built, run, and measured against the unmodified baseline — same hardware, same inputs, paired runs in alternating order across multiple seeds, so noise cancels instead of masquerading as a result.

✓

Correctness Is a Gate

Patched and unpatched systems are fed identical inputs and compared exactly — hashes, dtypes, edge cases down to the sign of a floating-point zero. Any observable change means automatic rejection.

📊

Statistics Before Headlines

Every reported number carries confidence bounds from repeated measurements. A flashy median with a shaky interval doesn't get promoted, no matter how good it looks.

🚫

It Rejects Its Own Ideas

One clever kernel rewrite showed a small win in one phase and a regression in another — AutoR&D flagged the mixed evidence and held it back itself. Negative results are kept, not buried.

What It Found

We didn't hand AutoR&D toy problems — we aimed it at two of the most heavily used and heavily optimized libraries in the Python data/AI ecosystem, plus one of our own production systems. It found something real in all three.

1
Open Source · Vector Search

hnswlib: a clean +4% in the engine behind AI retrieval

+4.1% median query throughput Bit-for-bit identical results

hnswlib powers vector search inside databases, RAG pipelines, and recommendation systems, and has been tuned by experts for years — exactly why we chose it. AutoR&D found a remaining win in the batch query path: every query was paying a synchronization cost to borrow scratch memory from a shared pool. Its patch has each worker thread lease that scratch once and reuse it across the batch — roughly 4,000 lock operations collapsed to 32 in the diagnostic workload — while leaving the search logic untouched.

The result: +4.1% median queries-per-second across three independently built indexes, faster in every paired run, with labels, distances, and recall verified identical to the byte.

2
Open Source · Dataframes

pandas: routing hot paths around work they don't need

4–28% faster primary workloads Up to +64.6% best case Up to 1.84× on nullable dtypes 136K checks, 0 mismatches

pandas must handle every data type, missing-value convention, and memory layout — and that generality has a cost: hot operations sometimes do conversion, masking, and copying work even when the data is already in ideal form. AutoR&D's answer: check first, then take the express lane. A narrowly guarded fast path serves data whose layout qualifies; everything else falls through to pandas' unchanged general implementation.

Counting and de-duplicating strings. For nullable string columns, duplicated() and value_counts() now hand their backing array straight to pandas' own hashing kernel — 4.4–12.2% faster on million-value workloads, with peak memory for value_counts down by about a third. Total change: a 28-line diff.

Row-wise math. sum, prod, min, and max across rows used to allocate fresh intermediate arrays for every internal block; the patch folds blocks into one reused accumulator. That's 12–28% faster on a typical 100,000-row mixed frame — and up to 64.6% on the fragmented frames real pipelines accumulate.

Typical mixed frame (100K rows) Fragmented frame (32 blocks)

Row-wise math on nullable dtypes. pandas' nullable integer, float, and boolean columns — including their Arrow-backed variants — take a different route for row-wise sum, prod, min, and max: the frame is flattened and run through the groupby kernels, which meant first building a "row label" for every single element — a throwaway array as large as the frame itself — just to tell the kernel which row each value belongs to. AutoR&D's patch views the existing data and mask buffers in the layout the kernel already expects and reduces with a single group, so that label array is never allocated and the kernels and reduction order stay exactly as they were. Across pandas' own 40-cell benchmark that's 1.22–1.84× faster (median 1.38×) with every confidence interval above parity, and 12–15% lower peak memory on a 10-million-element frame.

What makes this upstream-ready isn't the speed — it's the verification: 1,910 differential test cases for the first two patches and 134,064 more for the nullable-dtype patch, each comparing patched and unpatched pandas on identical inputs — from Unicode and emoji to integer overflow, infinities, min_count edge cases, and the sign bit of zero. Every output matched exactly, and anything unusual simply takes the original code path.

3
Salesforce Internal · LLM Training

SFR-RL: taming memory and speed in our own RL stack

−39% peak training memory Up to 3.14× generation throughput Token-for-token identical outputs

The most satisfying test was pointing AutoR&D at our own infrastructure: SFR-RL, the reinforcement-learning stack Salesforce AI Research uses to post-train large models. (SFR-RL is internal, so we share the results here rather than the recipes.)

Memory: from roulette to guarantees. In RL training the model generates its own training data, so each step's memory footprint is drawn fresh every update — and one unlucky draw can blow past GPU memory late in an expensive run. AutoR&D's improvements make peak memory predictable and bounded by configuration rather than luck: on a demanding long-context workload, peak memory fell from 128.5 GiB — an out-of-memory crash — to a stable 78.6 GiB across 19 consecutive updates, with the training computation itself unchanged.

Throughput: the same answers, three times faster. On the serving side of the loop, AutoR&D cut median time per generated token by 60–69% across four workload types — up to 3.14× baseline throughput on long-output workloads — with the accelerated path verified to produce exactly the same tokens, request by request, in every confirmation run.

💡 Why it matters

Faster iterations and no more lost runs — our researchers feel this one every day. And because outputs are verified identical, the speedups are free: no accuracy trade-off, no behavioral drift.

What's Next

These three artifacts are a beginning, not a victory lap. We're scaling AutoR&D along three axes: more targets — from data infrastructure to the wider open-source ecosystem our customers' AI stacks depend on, and more of Salesforce's own platform; deeper autonomy — longer research arcs where one discovery informs the next hypothesis; and open contribution — packaging discoveries as upstream pull requests with the full evidence attached.


We think the future of agentic AI isn't just agents that do what we ask — it's agents that find improvements we didn't know to ask for, and prove they're real. AutoR&D is our first step there.
