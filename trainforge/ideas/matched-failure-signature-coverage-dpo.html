Matched Failure-Signature Coverage DPO

Choose executable negative programs for the distinct failures they expose, then compare that allocation against a compute-matched uniform control.

01 · Thesis

Hard negatives should cover different ways code can fail.

Executable-mutant preference training often samples any incorrect program that a public test kills. That treats ten mutants failing the same check as ten equally useful lessons, even when another mutant would expose a different semantic weakness.

Hold the task, correct program, batch slot, and optimizer budget fixed; change only how the rejected program is allocated from one verified mutant pool.

The treatment greedily adds the mutant with the largest new coverage of (AST mutation family, failed-check index). The control draws killed mutants uniformly with a fixed seed. Because both arms use the same verified pool and matched schedule, the comparison isolates the allocation rule instead of the generic benefit of executable negatives.

02 · Research position

A performance-first, incremental hypothesis.

DPO, mutation testing, hard-negative mining, and submodular coverage are established ideas. The narrow contribution is their controlled combination: marginal failure-signature coverage versus seeded uniform allocation under an identical executable pool and optimizer schedule.

The two-pass internal review scored the proposal 3.4 and 4.0. It is therefore presented as an honest incremental method worth measuring—not as a verified-novel result.

03 · Real-data construction

From source programs to a frozen preference pool.

Target and preflight rows are excluded from fitting before any mutant is generated.

01

Fix the eligible tasks

Start from 120 MBPP-sanitized training rows and remove the eight manifest-bound diagnostic and complete-fitting exclusions, leaving 112 eligible source tasks.

02

Verify the references

In a networkless sandbox, require each reference program to compile and pass every listed public training check. A task enters the pool only after that executable proof.

03

Create bounded mutants

Enumerate four frozen single-site AST edit families. Retain only loading programs killed by at least one public check; the sealed pool contains 633 pairs across 92 tasks.

04

Freeze both allocations

Build a seeded-uniform control and a coverage-greedy treatment from the same pool, then bind each arm to an immutable 480-slot schedule.

04 · Objective

Ordinary DPO; a different rejected-example curriculum.

z = β[(log πθ(y+) − log πθ(y−)) − (log πref(y+) − log πref(y−))]

L = −log σ(z)

The correct reference program is y+; an execution-killed mutant is y−. The loss is identical in both arms. Only the frozen negative allocation changes.

05 · Training contract

Matched down to the global slot.

  • Qwen3.5-35B-A3B with rank-16, alpha-32 all-linear LoRA
  • BF16 ZeRO-3 over eight GPUs; learning rate 5×10⁻⁵
  • Exactly 60 optimizer updates and global batch eight per arm
  • Same task, prompt, correct program, order, seed, and 480 batch slots
  • Independent starts from the same unadapted base
  • Immutable checkpoints and telemetry at updates 20, 40, and 60

06 · Deployment

The mutation machinery disappears.

  • Reload the selected adapter on the unchanged Qwen3.5-35B-A3B base
  • Generate ordinary source code through the existing interface
  • Add no mutation engine, test feedback, verifier, search, or Python tool at inference
  • Keep the 32K response allowance inside a 40,960-token training context

07 · What would falsify it?

Coverage must beat the matched control.

  • The treatment is flat or worse than uniform allocation
  • Coverage gains concentrate in one mutation family or a few source tasks
  • The adapter improves public-style checks but not independently held-out code
  • Any row, schedule, checkpoint, or scorer identity fails its frozen receipt
  • Runtime errors prevent all 60 evidenced updates in either arm
