Censored Competing-Risk Pivot Optimization

Train pivot timing without pretending that every budget-exhausted trajectory made a wrong choice. “Exploit the current anchor” and “switch research field” are modeled as competing events; unfinished trajectories are right-censored.

Method at a glance Separate observed decisions from unobserved futures.
Training unit
Budget-indexed decision state
Outcomes
Exploit · switch · censored

01 · Training problem

A capped trajectory hides what would have happened next.

When a tool budget expires, the log records neither successful anchor exploitation nor a productive field switch. Broadcasting terminal failure backward converts this missing future into a negative label for every earlier decision.

This method treats pivot learning as a time-to-event problem. It preserves three distinct states: an observed exploit event, an observed switch event, and a trajectory that ended while the next decision was still unknown.

02 · Learning principle

Do not invent a terminal label for censored work.

Learn separate hazards for exploiting the current evidence anchor and switching fields, while allowing budget exhaustion to end observation without becoming either event.

03 · Training recipe

Turn each trajectory into a competing-risk record.

Event labels must come from environment-visible transitions, not a model’s account of its own strategy.

State timeline

Index every research decision

Retain tool-call time, remaining budget, current evidence anchor, field identifier, next action, and the first later verified event. The same event detector and time convention must be used across every training arm.

Event construction

Make exploit and switch exclusive

An exploit event means the trajectory successfully acts within the current evidence anchor; a switch event means it leaves for a distinct research field. Once the first event occurs, the record leaves the risk set.

Censoring

Stop observation without assigning failure

If the declared budget ends before either event is observed, mark the record right-censored at that time. The unknown next event contributes no fabricated exploit or switch label.

Objective

Fit cause-specific decision hazards

Estimate separate exploit and switch terms over states still at risk, with a survival term while neither event occurs. Use bounded, logged censoring-aware weights rather than broadcasting one terminal reward through the trace.

04 · Update sequence

From raw trace to pivot supervision

  1. Reconstruct the anchor and field state at each eligible tool decision.
  2. Scan forward to the first environment-verified exploit or switch event.
  3. If neither occurs, close the observation as censored at budget exhaustion.
  4. Build the at-risk set up to the observed event or censoring time.
  5. Compute separate exploit, switch, and no-event contributions.
  6. Use the resulting censoring-aware signal on the local stay-versus-switch action span.

05 · Policy update

Credit only the decision the event can identify

  • Exploit evidence affects the current-anchor action signal.
  • Switch evidence affects the field-pivot action signal.
  • Censored endings contribute exposure time, not a negative event.
  • Weights are clipped or bounded under the declared run contract.
  • The exact mapping from hazard signal to token loss is logged for fidelity review.

06 · Deployment behavior

The annotation pipeline is training-only

  • The trained model keeps the existing research tool interface.
  • No event annotator is called during inference.
  • No survival-analysis service is added to the runtime path.
  • Pivot behavior is carried by the updated policy.
  • Runtime budget accounting remains environment-owned.

07 · Controls and fidelity

Prove the gain is not label leakage or extra compute

  • Match trajectories, checkpoint, order, examples, and update budget.
  • Keep exploit and switch definitions mutually exclusive and frozen.
  • Ablate censoring-aware weights against terminal-failure broadcasting.
  • Publish weight distributions and effective sample size.
  • Current behavioral evidence does not yet prove the authored event pipeline ran faithfully.

09 · Implementation checklist

What must be inspectable in a faithful run

  • Publish event definitions with positive and boundary-case examples.
  • Verify that exhaustion produces a censored record, never a failed-event label.
  • Trace censoring weights into the exact policy-loss terms they modify.
  • Keep performance, mechanism fidelity, and novelty as separate records.
